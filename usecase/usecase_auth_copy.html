CHƯƠNG 3. ĐẶC TẢ USECASE AUTH

1. Use Case Specification: Đăng ký tài khoản (UC-6A)

Use Case Name Use Case ID Date Created Created By
Đăng ký tài khoản UC-6A 15/05/2026 Võ Hoàng Phúc
Primary Actors Secondary Actors
Người dùng (Độc giả/Học sinh) Hệ thống Email (SMTP Server)

3.1. Brief Description
Usecase này mô tả quá trình người dùng đăng ký một tài khoản mới trên hệ thống. Người dùng nhập thông tin email và mật khẩu tại trang Đăng ký. Hệ thống sẽ kiểm tra tính hợp lệ, lưu trữ thông tin tài khoản (trạng thái chờ xác thực) vào cơ sở dữ liệu MySQL và tự động gửi một email chứa liên kết kích hoạt đến email của người dùng.

3.2. Pre-conditions
1. Hệ thống đang hoạt động bình thường với kết nối ổn định đến MySQL.
2. Dịch vụ gửi Email (SMTP) được cấu hình đúng và đang sẵn sàng.

3.3. Trigger
Người dùng điền đầy đủ thông tin vào form trên trang Đăng ký (RegisterPage.tsx) và nhấp vào nút "Đăng ký".

3.4. Post-conditions
1. Thông tin người dùng được lưu vào bảng users trong MySQL với trạng thái pending.
2. Một email chứa mã token kích hoạt được gửi đến hòm thư của người dùng.

3.5. Normal Flow: Đăng ký thành công (6A.1)
6A.1.1: RegisterPage.tsx: Người dùng nhập thông tin và nhấp vào nút Đăng ký.
6A.1.2: RegisterPage.tsx: gọi hàm register trong authService.ts.
6A.1.3: authService.ts: gọi API POST /api/auth/register đến AuthController.java.
6A.1.4: AuthController.java: gọi AuthService.java (hàm register).
6A.1.5: AuthService.java: truy vấn kiểm tra và lưu User vào MySQL.
6A.1.6: MySQL: trả về User Entity cho AuthService.java.
6A.1.7: AuthService.java: gửi email kích hoạt qua dịch vụ SMTP.
6A.1.8: AuthService.java: trả kết quả thông tin User cho AuthController.java.
6A.1.9: AuthController.java: trả HTTP status 200 cho authService.ts.
6A.1.10: authService.ts: trả dữ liệu kết quả về cho RegisterPage.tsx.
6A.1.11: RegisterPage.tsx: hiển thị thông báo "Đăng ký thành công. Vui lòng kiểm tra email...".

3.6. Alternative Flows (Luồng Phụ)
3.6.1. Email đã tồn tại (6A.2)
Tại bước 6A.1.5, hệ thống phát hiện email đã được sử dụng.
6A.2.1: AuthService.java: truy vấn kiểm tra Email tại MySQL.
6A.2.2: MySQL: trả về trạng thái email đã tồn tại cho AuthService.java.
6A.2.3: AuthService.java: ném lỗi ApiException (mã 400 hoặc 409) cho AuthController.java.
6A.2.4: AuthController.java: trả lỗi về cho authService.ts.
6A.2.5: authService.ts: ném lỗi về cho giao diện RegisterPage.tsx.
6A.2.6: RegisterPage.tsx: hiển thị thông báo lỗi "Email đã được đăng ký" ngay trên form.

3.7. Exceptions
- Dịch vụ SMTP thất bại không thể gửi email.
- Mất kết nối đến cơ sở dữ liệu MySQL.

3.8. Includes
- Giao diện đăng ký (RegisterPage.tsx).
- API xử lý đăng ký của Spring Boot (AuthController, AuthService).
- Cơ sở dữ liệu MySQL (bảng users, roles).

3.9. Assumptions
- Thiết bị người dùng có kết nối mạng internet.
- Người dùng nhập đúng định dạng email cá nhân của mình.

3.10. Giải thích cơ chế truy vấn CSDL (Database Query)
Auth module sử dụng Spring Data JPA (JpaRepository) — không viết SQL thuần. Hibernate tự sinh câu truy vấn từ tên method và Entity mapping. Khi xử lý UC-6A, hệ thống thực hiện tuần tự các truy vấn sau:

1. Kiểm tra email đã tồn tại (UserRepository.findByEmail)
- Tương đương SQL:
SELECT * FROM users WHERE email = ? LIMIT 1
- Giải thích: Spring Data tự sinh query từ method name findByEmail(String email) trong UserRepository. Kết quả Optional<UserEntity> — nếu có giá trị thì email đã tồn tại, ném ApiException 409 CONFLICT. Nếu trạng thái là pending, ném lỗi khác biệt (EMAIL_ALREADY_EXISTS_PENDING).

2. Lấy Role mặc định cho User mới (RoleRepository.findByCode)
- Tương đương SQL:
SELECT * FROM roles WHERE code = 'student' LIMIT 1
- Giải thích: Mỗi User đăng ký mới được gán Role student mặc định. Nếu seed dữ liệu bảng roles chưa có bản ghi này, hệ thống ném 500 ROLE_SEED_MISSING.

3. Lưu User mới vào DB (UserRepository.save)
- Tương đương SQL:
INSERT INTO users (id, email, password_hash, full_name, grade, school, status, ...) VALUES (?, ?, ?, ?, ?, ?, 'pending', ...)
INSERT INTO user_roles (user_id, role_id) VALUES (?, ?)
- Giải thích: UserEntity map bảng users. Quan hệ ManyToMany với bảng roles qua join table user_roles được Hibernate xử lý tự động khi save(). Trường id là BINARY(16) — UUID được chuyển thành byte array bằng UuidBytes.fromUuid(UUID.randomUUID()). User được tạo với status = 'pending' — chưa kích hoạt.

4. Lưu Token kích hoạt Email (AuthEmailTokenRepository.save)
- Tương đương SQL:
INSERT INTO auth_email_tokens (user_id, token_hash, token_type, expires_at) VALUES (?, ?, 'email_verification', ?)
- Giải thích: Raw token được hash bằng SHA-256 trước khi lưu (không lưu plain text). expires_at được tính từ thời điểm hiện tại cộng thêm TTL cấu hình (mặc định 10 phút). Link xác minh gửi đến email chứa raw token — backend sẽ hash lại và so sánh.

2. Use Case Specification: Đăng nhập (UC-6B)

Use Case Name Use Case ID Date Created Created By
Đăng nhập UC-6B 15/05/2026 Võ Hoàng Phúc
Primary Actors Secondary Actors
Người dùng (Độc giả/Admin) Google / Facebook Auth Servers

3.1. Brief Description
Usecase này mô tả quá trình người dùng truy cập vào hệ thống. Người dùng có thể đăng nhập bằng tài khoản (Email/Mật khẩu) đã đăng ký hoặc đăng nhập thông qua bên thứ 3 (Google/Facebook). Hệ thống sẽ xác thực, cấp JWT Token lưu trong HttpOnly Cookie để duy trì phiên đăng nhập an toàn (miễn dịch với XSS), và định tuyến người dùng vào trang chủ hoặc trang quản trị tuỳ theo phân quyền.

3.2. Pre-conditions
1. Tài khoản của người dùng đã được đăng ký và kích hoạt thành công (nếu dùng Email).
2. Kết nối đến MySQL và API xác thực của Google/Meta hoạt động bình thường.

3.3. Trigger
Người dùng điền Email/Mật khẩu và nhấp nút "Đăng nhập", hoặc nhấp vào nút "Đăng nhập bằng Google/Facebook" trên màn hình LoginPage.tsx.

3.4. Post-conditions
1. Hệ thống sinh ra JWT Token (Access Token và Refresh Token) hợp lệ.
2. Access Token và Refresh Token được trình duyệt lưu tự động dưới dạng HttpOnly Cookie (JavaScript không thể đọc được — miễn dịch với XSS).
3. Thông tin hiển thị của người dùng (tên, avatar, role) được lưu vào localStorage để UI phản hồi tức thì.
4. Người dùng được chuyển hướng đến trang tương ứng với Role của mình (Student → trang chủ, Admin → /admin/dashboard).

3.5. Normal Flow: Đăng nhập bằng Email thành công (6B.1)
6B.1.1: LoginPage.tsx: Người dùng nhập Email, Mật khẩu và nhấp nút Đăng nhập.
6B.1.2: LoginPage.tsx: gọi hàm login trong AuthContext.tsx (login trả về AuthResponse).
6B.1.3: authService.ts: gọi POST /api/auth/login đến AuthController.java.
6B.1.4: AuthController.java: gọi AuthService.java (hàm login).
6B.1.5: AuthService.java: truy vấn kiểm tra thông tin và đối chiếu mật khẩu tại MySQL.
6B.1.6: MySQL: trả về kết quả hợp lệ cho AuthService.java.
6B.1.7: AuthService.java: tạo JWT Token và trả về cho AuthController.java.
6B.1.8: AuthController.java: đặt Access Token và Refresh Token vào HttpOnly Cookie trong HTTP Response, trả HTTP 200 kèm User info cho authService.ts.
6B.1.9: authService.ts: lưu thông tin User (tên, avatar, role) vào localStorage để UI phản hồi tức thì. Token được trình duyệt lưu tự động qua Cookie. Trả AuthResponse (có chứa role) về cho LoginPage.tsx.
6B.1.10: LoginPage.tsx: đọc role từ AuthResponse trả về, chuyển hướng người dùng đến trang chủ hoặc /admin/dashboard.

3.6. Alternative Flows (Luồng Phụ)
3.6.1. Đăng nhập bằng Google (6B.2)
6B.2.1: OAuthButtons.tsx: Nhấp nút Đăng nhập bằng Google.
6B.2.2: Google Server: Trả về credential (id_token) cho giao diện.
6B.2.3: OAuthButtons.tsx: gọi hàm loginWithGoogle trong AuthContext.tsx.
6B.2.4: authService.ts: gọi POST /api/auth/oauth/google đến AuthController.java.
6B.2.5: AuthController.java: gọi SocialAuthService.java.
6B.2.6: SocialAuthService.java: Gọi API xác thực token ngược lại với Server Google.
6B.2.7: Google Server: Trả về thông tin User hợp lệ (Email, Tên, Avatar).
6B.2.8: SocialAuthService.java: Upload avatar từ Google URL lên Cloudinary để lưu trữ vĩnh viễn.
6B.2.9: SocialAuthService.java: Truy vấn và lưu User vào MySQL (avatarUrl là Cloudinary URL).
6B.2.10: MySQL: Trả về User Entity.
6B.2.11: SocialAuthService.java: Tạo JWT Token và trả về.
6B.2.12: AuthController.java: đặt Access Token và Refresh Token vào HttpOnly Cookie trong HTTP Response, trả HTTP 200 kèm User info.
6B.2.13: authService.ts: lưu thông tin User vào localStorage. Trả AuthResponse (có chứa role) về cho OAuthButtons.tsx.
6B.2.14: OAuthButtons.tsx: đọc role từ AuthResponse trả về, chuyển hướng về trang chủ hoặc /admin/dashboard.

3.6.2. Đăng nhập bằng Facebook (6B.3)
6B.3.1: OAuthButtons.tsx: Nhấp nút Đăng nhập bằng Facebook.
6B.3.2: Facebook SDK: Gọi FB.login() -> Facebook Server trả về access_token cho giao diện.
6B.3.3: OAuthButtons.tsx: gọi hàm loginWithFacebook trong AuthContext.tsx.
6B.3.4: authService.ts: gọi POST /api/auth/oauth/facebook đến AuthController.java.
6B.3.5: AuthController.java: gọi SocialAuthService.java.
6B.3.6: SocialAuthService.java: Gọi Meta debug_token API (app_id|app_secret) để xác thực token: kiểm tra is_valid=true, app_id khớp, token chưa hết hạn.
6B.3.7: Facebook Server: Xác nhận token hợp lệ.
6B.3.8: SocialAuthService.java: Gọi Graph API /me với fields=id,name,email,picture.width(200).height(200) để lấy Profile.
6B.3.9: Facebook Server: Trả về thông tin User hợp lệ (Email, Tên, Avatar).
6B.3.10: SocialAuthService.java: Upload avatar từ Facebook lên Cloudinary (nếu có).
6B.3.11: SocialAuthService.java: Truy vấn và lưu User vào MySQL (avatarUrl là Cloudinary URL).
6B.3.12: MySQL: Trả về User Entity.
6B.3.13: SocialAuthService.java: Tạo JWT Token và trả về.
6B.3.14: AuthController.java: đặt Access Token và Refresh Token vào HttpOnly Cookie, trả HTTP 200 kèm User info.
6B.3.15: authService.ts: lưu thông tin User vào localStorage. Trả AuthResponse (có chứa role).
6B.3.16: OAuthButtons.tsx: đọc role, chuyển hướng về trang chủ hoặc /admin/dashboard.

3.6.3. Sai thông tin xác thực (6B.4)
Tại bước 6B.1.5, mật khẩu hoặc email không đúng.
6B.4.1: AuthService.java: truy vấn xác thực tại MySQL.
6B.4.2: MySQL: trả về trạng thái không hợp lệ.
6B.4.3: AuthService.java: ném lỗi ApiException (mã 401 Unauthorized).
6B.4.4: AuthController.java: trả lỗi 401 cho authService.ts.
6B.4.5: authService.ts: ném lỗi về cho LoginPage.tsx.
6B.4.6: LoginPage.tsx: hiển thị thông báo "Tài khoản hoặc mật khẩu không chính xác".

3.7. Exceptions
- Hệ thống giới hạn rate-limit (authRateLimiter) khi người dùng spam đăng nhập quá nhiều lần.
- Google/Facebook token không hợp lệ/hết hạn → INVALID_SOCIAL_TOKEN.
- Facebook không trả về email → SOCIAL_EMAIL_REQUIRED.
- Tài khoản bị khóa tạm thời (15 phút) sau 5 lần đăng nhập sai liên tiếp (account lockout).
- Tài khoản bị vô hiệu hóa → ACCOUNT_DISABLED (403 Forbidden).
- Tài khoản chưa xác minh email → EMAIL_NOT_VERIFIED (403 Forbidden).

3.8. Includes
- LoginPage.tsx (Form đăng nhập Email), OAuthButtons.tsx (Google & Facebook SDK).
- AuthController.java (AuthService / SocialAuthService).
- Cơ sở dữ liệu MySQL (bảng users, user_social_providers, roles).
- Google Identity Services SDK / Facebook JavaScript SDK (phía client).
- Google tokeninfo API / Meta debug_token + Graph API (phía server).
- Cloudinary (lưu trữ avatar vĩnh viễn).

3.9. Assumptions
- Thiết bị người dùng hỗ trợ JavaScript (cho OAuth SDK).
- Người dùng có tài khoản Google/Facebook hoặc email hợp lệ.
- Google Client ID và Facebook App ID được cấu hình trong biến môi trường.
- Trình duyệt hỗ trợ HttpOnly Cookie và không chặn third-party cookie (SameSite).

3.10. Giải thích cơ chế truy vấn CSDL (Database Query)
Auth module sử dụng Spring Data JPA cho các truy vấn. Khi thực hiện luồng đăng nhập (UC-6B), hệ thống thực hiện các query sau:
1. Kiểm tra email/username – UserRepository.findByEmail → SELECT * FROM users WHERE email = ? LIMIT 1.
2. Kiểm tra mật khẩu – Hibernate tự sinh câu truy vấn dựa trên password_hash và so sánh trong Java.
3. Lấy Role – RoleRepository.findByCode → SELECT * FROM roles WHERE code = ? LIMIT 1.
4. Tạo JWT Token – JwtService.createAccessToken / createRefreshToken — JWT được ký với secret key, không lưu trong DB. Token được đặt vào HttpOnly Cookie trong HTTP Response (access_token path=/, refresh_token path=/api/auth/refresh). Tất cả các query này được Hibernate quản lý, sử dụng các Entity mapping đã định nghĩa trong UserEntity, RoleEntity và AuthTokenEntity.

3. Use Case Specification: Quên mật khẩu (UC-6C)

Use Case Name Use Case ID Date Created Created By
Quên mật khẩu UC-6C 15/05/2026 Võ Hoàng Phúc
Primary Actors Secondary Actors
Người dùng Hệ thống Email (SMTP Server)

3.1. Brief Description
Usecase này hỗ trợ người dùng đã quên mật khẩu lấy lại quyền truy cập. Người dùng cung cấp email tài khoản, hệ thống sẽ gửi một liên kết bảo mật chứa token xác thực. Khi nhấp vào liên kết, người dùng có thể nhập mật khẩu mới để thay thế mật khẩu cũ.

3.2. Pre-conditions
1. Người dùng đã từng đăng ký tài khoản trong hệ thống.
2. Hệ thống Email (SMTP) hoạt động ổn định.

3.3. Trigger
Người dùng điền email vào trang ForgotPasswordPage.tsx và nhấn "Gửi", sau đó nhấp vào link trong email để tới trang ResetPasswordPage.tsx nhập mật khẩu mới.

3.4. Post-conditions
1. Chuỗi Hash mật khẩu của người dùng được cập nhật mới hoàn toàn trong bảng users của MySQL.
2. Token reset mật khẩu cũ bị vô hiệu hoá/xoá bỏ để ngăn tái sử dụng.

3.5. Normal Flow: Yêu cầu đặt lại và Cập nhật mật khẩu (6C.1)
6C.1.1: ForgotPasswordPage.tsx: Nhập email và nhấn nút Gửi.
6C.1.2: ForgotPasswordPage.tsx: gọi hàm forgotPassword trong authService.ts.
6C.1.3: authService.ts: gọi POST /api/auth/forgot-password đến AuthController.java.
6C.1.4: AuthController.java: gọi AuthService.java (hàm requestPasswordReset).
6C.1.5: AuthService.java: kiểm tra sự tồn tại của email trong MySQL.
6C.1.6: MySQL: trả về User Entity hợp lệ.
6C.1.7: AuthService.java: tạo token và gửi email reset qua SMTP.
6C.1.8: AuthService.java: trả kết quả thành công cho AuthController.java.
6C.1.9: AuthController.java: trả HTTP 200 cho authService.ts.
6C.1.10: authService.ts: trả dữ liệu cho ForgotPasswordPage.tsx.
6C.1.11: ForgotPasswordPage.tsx: hiển thị thông báo "Vui lòng kiểm tra hộp thư của bạn" kèm email người dùng.
6C.1.12: ResetPasswordPage.tsx: Người dùng nhấp vào link từ email, nhập mật khẩu mới và nhấn nút Đặt lại.
6C.1.13: ResetPasswordPage.tsx: gọi hàm resetPassword trong authService.ts.
6C.1.14: authService.ts: gọi POST /api/auth/reset-password đến AuthController.java.
6C.1.15: AuthController.java: gọi AuthService.java (hàm resetPassword).
6C.1.16: AuthService.java: xác thực token an toàn và mã hoá mật khẩu mới lưu vào MySQL.
6C.1.17: MySQL: xác nhận cập nhật thành công và đánh dấu token đã dùng (used_at).
6C.1.18: AuthService.java: trả kết quả cho AuthController.java.
6C.1.19: AuthController.java: trả HTTP 200 cho authService.ts.
6C.1.20: authService.ts: trả dữ liệu thành công cho ResetPasswordPage.tsx.
6C.1.21: ResetPasswordPage.tsx: hiển thị thông báo thành công và chuyển hướng người dùng về trang Đăng nhập.

3.6. Alternative Flows
- Nếu Email không tồn tại, hệ thống vẫn trả về HTTP 200 thành công để chống hacker dò quét (Anti-enumeration). Frontend hiển thị "Vui lòng kiểm tra hộp thư của bạn" trong mọi trường hợp.

3.7. Exceptions
- Token xác thực ở Giai đoạn 2 đã hết hạn hoặc không hợp lệ, hệ thống báo lỗi từ chối cập nhật mật khẩu. Mật khẩu mới không tuân thủ chính sách bảo mật (quá ngắn, thiếu ký tự).

3.8. Includes
- ForgotPasswordPage.tsx, ResetPasswordPage.tsx.
- AuthController, AuthService (AuthService.java).
- AuthEmailTokenRepository (bảng auth_email_tokens).
- Hệ thống Email (SMTP).

3.9. Assumptions
- Người dùng có quyền truy cập vào email đã đăng ký.
- Hệ thống Email (SMTP) được cấu hình đúng.

3.10. Giải thích cơ chế truy vấn CSDL (Database Query)
Đối với luồng quên mật khẩu (UC-6C) hệ thống thực hiện các query sau:
1. Kiểm tra tồn tại email – UserRepository.findByEmail → SELECT * FROM users WHERE email = ? LIMIT 1.
2. Tạo và lưu token reset – AuthEmailTokenRepository.save → INSERT INTO auth_email_tokens (user_id, token_hash, token_type, expires_at) VALUES (?, ?, 'password_reset', ?) (Token type là 'password_reset' — khác với 'email_verification' dùng cho đăng ký).
3. Khi người dùng gửi mật khẩu mới, xác thực token – AuthEmailTokenRepository.findByTokenHashAndTokenType → SELECT * FROM auth_email_tokens WHERE token_hash = ? AND token_type = 'password_reset' LIMIT 1. Hết hạn được kiểm tra ở Java layer: token.getExpiresAt().isAfter(Instant.now()).
4. Cập nhật mật khẩu – UserRepository.save (Hibernate generates UPDATE users SET password_hash = ? WHERE id = ?).
5. Vô hiệu hoá token đã dùng – AuthEmailTokenRepository.save (setUsedAt) → UPDATE auth_email_tokens SET used_at = NOW() WHERE id = ? (Token không bị xóa khỏi DB — chỉ đánh dấu used_at để ngăn tái sử dụng). Các câu truy vấn này đều được Hibernate sinh tự động dựa trên Entity và Repository đã định nghĩa.

4. Use Case Specification: Đăng xuất (UC-6D)

Use Case Name Use Case ID Date Created Created By
Đăng xuất UC-6D 17/05/2026 Võ Hoàng Phúc
Primary Actors Secondary Actors
Người dùng đã đăng nhập Không có

3.1. Brief Description
Usecase này mô tả quá trình người dùng kết thúc phiên làm việc. Hệ thống xóa HttpOnly Cookie chứa JWT phía server, xóa thông tin hiển thị trong localStorage phía client và reset React state ngay lập tức — không cần reload trang. Thiết kế defensive đảm bảo logout luôn thành công kể cả khi API backend không phản hồi.

3.2. Pre-conditions
1. Người dùng đang trong trạng thái đã đăng nhập (isAuthenticated = true).
2. HttpOnly Cookie access_token và refresh_token đang tồn tại trong trình duyệt.

3.3. Trigger
Người dùng nhấp vào nút "Đăng xuất" trên AppHeader.tsx (desktop dropdown hoặc mobile menu).

3.4. Post-conditions
1. HttpOnly Cookie access_token và refresh_token bị xóa khỏi trình duyệt (maxAge=0).
2. Thông tin User được xóa khỏi localStorage.
3. React state currentUser = null — isAuthenticated = false ngay lập tức.
4. Người dùng được chuyển hướng về trang chủ (/) mà không cần reload trang.
5. ProtectedRoute tự động redirect về /login nếu người dùng cố truy cập trang yêu cầu xác thực.

3.5. Normal Flow: Đăng xuất thành công (6D.1)
6D.1.1: AppHeader.tsx: Người dùng nhấp nút "Đăng xuất" (desktop dropdown hoặc mobile menu).
6D.1.2: AppHeader.tsx: gọi await logout() từ AuthContext.tsx — bắt buộc await để navigate chạy sau khi state đã clear.
6D.1.3: AuthContext.tsx: gọi authService.logout() trong khối try — nếu lỗi API, finally vẫn chạy.
6D.1.4: authService.ts: gọi POST /api/auth/logout đến AuthController.java.
6D.1.5: AuthController.java: gọi clearAuthCookies() — đặt maxAge=0 trên access_token (path=/) và refresh_token (path=/api/auth/refresh).
6D.1.6: AuthController.java: trả HTTP 200 kèm message "Đăng xuất thành công."
6D.1.7: authService.ts: gọi clearStoredUser() — xóa auth_user khỏi localStorage (chạy trong finally, luôn thực thi).
6D.1.8: AuthContext.tsx: gọi setCurrentUser(null) — reset React state (chạy trong finally, luôn thực thi).
6D.1.9: AppHeader.tsx: gọi navigate('/') — chuyển hướng về trang chủ.
6D.1.10: Giao diện cập nhật tức thì: header hiển thị nút Đăng nhập, ProtectedRoute redirect nếu cần.

3.6. Alternative Flows (Luồng Phụ)
3.6.1. API Backend không phản hồi (6D.2)
Tại bước 6D.1.4, API lỗi (network down, backend restart...).
6D.2.1: authService.ts: catch block bắt lỗi API — bỏ qua, không throw lên caller.
6D.2.2: authService.ts: finally block vẫn chạy — xóa localStorage.
6D.2.3: AuthContext.tsx: finally block vẫn chạy — setCurrentUser(null).
6D.2.4: Người dùng được logout thành công phía client. Cookie HttpOnly sẽ tự hết hạn theo maxAge trên server.
Kết quả: Giao diện không bao giờ bị đơ (hang) dù API có lỗi.

3.7. Exceptions
- Không có exception nghiêm trọng: thiết kế defensive đảm bảo logout luôn hoàn thành phía client.
- Trường hợp duy nhất chưa xử lý: Cookie HttpOnly phía server không bị xóa nếu backend hoàn toàn down — cookie sẽ tự hết hạn sau 1 giờ (maxAge access_token).

3.8. Includes
- AppHeader.tsx (nút Đăng xuất desktop và mobile).
- AuthContext.tsx (hàm logout với try/finally).
- authService.ts (gọi API và xóa localStorage với try/catch/finally).
- AuthController.java (endpoint POST /api/auth/logout, hàm clearAuthCookies).
